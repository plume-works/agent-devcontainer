# GitHub automation

Everything GitHub runs for the repository: the workflows that check and build,
the composite actions they share, `renovate.json`, and
`pull_request_template.md`.

## Contains

[Workflows](github/workflows.md)

[Composite actions](github/actions.md)

## Public surface

- `renovate.json` — the self-hosted bot's repository config: automerges GitHub
  Actions updates, pre-commit hook revisions, the Renovate validator hook's
  `bunx` pin, lock-file maintenance, the `agent-desktop` digest (grouped so
  every copy moves in one PR), the `agent-opencode` digest in
  `opencode-compose-pins.yml`, Dev Container features (their lock regenerated by
  the post-upgrade script), and the Ansible role pins its custom regex managers
  extract from `# renovate:` comments under `ansible/roles/*/defaults/`,
  checksum-carrying `dev_tools` entries included; a further regex manager
  extracts that `bunx` pin from `.pre-commit-config.yaml`; runs
  `scripts/renovate-post-upgrade.sh` after every upgrade that touches the listed
  paths; disables Renovate for the Super-Linter family, which
  `/agentdev:sync-super-linter-tool-versions` moves by hand, and for the
  `ubuntu` base of `docker/ansible/Dockerfile`, which stays at 24.04
- `actionlint.yml` — runner labels newer than the pinned actionlint knows, read
  by the pre-commit hook and, through `super-linter-env.sh`, Super-Linter
- `.agent.metadata.json` — `iwe-map.digest_ignore` masks for runner labels and
  `agent-desktop` digests, so automerged bumps leave map digests unchanged
- `pull_request_template.md` — the verification sections [PR verification
  sections](../architecture/pr-verification-sections.md) describes

## How it works

`primary-checks.yml` is the entry workflow; it calls the reusable `reformat.yml`
and `ci.yml`. Three more workflows trigger independently on their own path
filters, `renovate.yml` runs the bot on a schedule, on every push to `main`, and
when a person edits its Dependency Dashboard or one of its PRs, and one is
manual. Knowledge validation has its own inner filter so the packaged IWE
scaffold tests run only when the scaffold, schemas, shared knowledge files, or
scaffold test moved. Agent-file validation includes every source path declared
by a codebase map doc, so source drift cannot skip the staleness gate.

## Invariants & gotchas

- The digest pins Renovate advances, `devcontainer-compose-pins.yml` and
  `opencode-compose-pins.yml`, live outside every path the image filter watches;
  that is what makes their automerge safe. Workflow container jobs pin the same
  digest and move with it.
- Actions are pinned to exact versions and audited by `zizmor` in pre-commit.
- The agent-file workflow's source filter stays aligned with codebase map
  frontmatter.
- `renovate.json` is itself validated, by a pre-commit hook and by
  `validate-renovate-config.yml`, both running the validator with `--no-global`
  so it applies the repository schema rather than the self-hosted one, at the
  hook's Renovate pin the bot also runs — see [Renovate config
  validation](../architecture/renovate-config-validation.md).
- The post-upgrade script's behavior and failure policy are [Renovate
  post-upgrade](../architecture/renovate-post-upgrade.md).
